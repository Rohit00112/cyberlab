# CyberLab Rust migration — October 20, 2026

## Current delivery

The existing IIC CyberLab project remains in `/cyberlab`. A new internal Rust service lives in `apps/security-core`, with a narrowly scoped Axum API:

- `GET /health`
- `POST /v1/verify`: SHA-256 flag verification with constant-time digest comparison, compatible with the existing trimmed-flag digest format
- `POST /v1/score`: deterministic standard, dynamic and first-blood calculations with bounded numeric inputs
- `POST /v1/lab-transition`: validates all lab-state transition arcs against the original state machine
- `POST /v1/authorization`: expands Keycloak realm roles into permissions and checks access using Rust RBAC rules
- `POST /v1/competition-transition`: validates organizer actions and time-based competition lifecycle changes in Rust
- `POST /v1/catalog/query`: pooled PostgreSQL query returning filtered, paginated challenge IDs and counts; students are restricted to published challenges
- `POST /v1/leaderboard`: pooled PostgreSQL global leaderboard aggregation, ordered by points and earliest correct solve

The FastAPI integration is in `apps/api/app/core/rust_engine.py`. Production/dev Compose services use internal Docker DNS and a shared secret. Rust traffic is not exposed by a host port, and malformed or unavailable service responses cause an HTTP 503. When running FastAPI without a Rust URL, its original Python path remains available for standalone development.

This is a **Rust core migration, not a full backend rewrite**. FastAPI continues to validate Keycloak OIDC tokens and run ORM, transactions, provisioning, competition APIs and research exports; Rust evaluates role-based permissions when configured. The Next.js UI and PostgreSQL schema remain compatible.

## Verified defects corrected

- API production image virtualenv location now matches its PATH.
- API image health check now uses the actual `/api/v1/health` endpoint.
- The duplicate stale `/health` Caddy route was removed.
- Celery production deployment now overrides the dev image and source bind mount.
- Python fallback flag verification now uses `hmac.compare_digest`.
- The score-event creation now targets the actual SQLAlchemy `ScoreEvent` columns. Its first-solve rank is corrected for the already-committed submission.
- The VPN peer and score-event SQLAlchemy models now match the actual October migration columns.
- Scoring, score-event creation, and submission persistence are now a single transaction. A scoring error rolls back the submission.
- Lab launch, reset, and asynchronous provisioning now follow valid `provisioning → starting → running` transitions.
- Scoring recording failures no longer disappear behind a broad exception handler.
- Role-based permission expansion and checks in API dependencies, challenge visibility, lab administration and research ownership use Rust when the internal core is configured. The Python permission policy remains available for standalone development. Rust outages fail closed with HTTP 503.

## Remaining work

October 30 badge reconciliation concurrency hardening: Rust-enabled automatic and manual competition finishes now share the same durable badge-retry checkpoint. Before a worker awards badges for an unacknowledged finish audit, it acquires a deterministic, event-specific PostgreSQL transaction advisory lock using a separate connection, then rechecks the acknowledgement while holding that lock. Other workers skip the in-flight event; the lock releases automatically after processing or process failure, and the next maintenance sweep retries unacknowledged work. Existing badge uniqueness and audit acknowledgements preserve idempotency on sequential retries. The 10-case native Rust/PostgreSQL suite verifies concurrent workers, manual acknowledgements and failure recovery, with 233 Python backend tests passing (10 opt-in skips). This does not yet provide a dedicated outbox with worker leases, workload metrics or exactly-once external notification delivery; full production/Celery multi-node validation remains outstanding.

October 30 automatic competition transitions: The maintenance sweep now delegates due scheduled-to-live and live-to-finished writes to the Rust core when enabled. Rust reads database time, locks due rows with `FOR UPDATE SKIP LOCKED` in bounded phases (250 rows per phase), rechecks the authoritative `auto` policy, and commits status updates plus `competition.auto_transition` audit details atomically. The two phases preserve the previous behavior for an already-ended scheduled competition. FastAPI uses append-only `competition.badges_reconciled` audit acknowledgements to retry badge evaluation for unacknowledged automatic or manual finish events on later sweeps, including after a crash following the Rust commit. The Python scheduler fallback remains available. The isolated live Rust/PostgreSQL suite passed all 9 cases, including competing sweep calls, restricted SQL, forced audit rollback and badge retry after a simulated failure; the backend suite passed 233 tests (9 opt-in skips), and Rust passed 26 unit tests, Clippy and format checks. The subsequent concurrency hardening above adds per-event worker claims; a dedicated outbox/lease and production/Celery integration still require validation.

October 30 manual competition transitions: Rust-enabled public organizer actions (`start_registration`, `schedule`, `start`, `finish`, `archive`) now use the internal Rust persistent writer. Under a competition row lock, Rust reads authoritative status/schedule and database time, applies the existing Rust transition policy, then commits the state update and mandatory `competition.transition` audit with action/from/to details atomically. It independently rechecks `competition.manage` and rejects the scheduler-only `auto` action on this route. The public FastAPI contract and Python fallback are preserved. On a successful finish, FastAPI continues the existing participant-badge follow-up after the Rust transaction; this is not a distributed transaction and remains a separate operational concern. Isolated native Rust/PostgreSQL tests verify all five actions, concurrency, RBAC, scheduled-state errors, restricted SQL and forced audit rollback; badge follow-up invocation is also checked. Restricted column grants are defined, but production provisioning remains unverified. Automatic scheduler persistence was migrated in the next milestone; badge acknowledgements remain in FastAPI.

October 30 leaderboard freeze/unfreeze: Rust-enabled public competition freeze and unfreeze endpoints now delegate to the internal Rust writer. The writer checks `competition.manage`, locks the competition row, updates `freeze_leaderboard`/`frozen_at` and writes the required event audit atomically. It preserves the public contract for all competition states, including repeated freeze/unfreeze calls, and returns via the original FastAPI response model. Isolated native Rust/PostgreSQL tests cover the public response, idempotent audits, token and RBAC denials, restricted-column SQL, and forced rollback of both operations. A restricted writer grant is defined but production provisioning and browser verification remain outstanding. Manual organizer transitions were migrated subsequently, retaining FastAPI badge follow-ups; automatic scheduler persistence was migrated subsequently.

October 29 competition teams: Rust-enabled public team create and join endpoints now delegate to the internal Rust writer, which rechecks `challenge.attempt`, registration/scheduled state, team enablement, registration and membership under a competition row lock. Team insertion, captain/member assignment, participant team link and required `team.create`/`team.join` audit commit together. The new Rust path rejects joining a second team or creating another team while already assigned. Python fallback remains available. Restricted column grants are defined for team writes; these must be provisioned and verified before deployment. Additional team administration/removal remains outstanding; freeze was migrated subsequently, while automated scheduler persistence and manual transitions were migrated subsequently.

October 29 participant registration: Rust-enabled public `POST /api/v1/competitions/{id}/register` and `/unregister` now delegate to internal Rust `/v1/competitions/register` and `/unregister`. Rust rechecks `challenge.attempt` role and competition existence under a row lock. Registration is permitted only in registration/scheduled state; the unique membership key prevents duplicate enrollment. Unregistration follows the legacy contract in any state, removes the participant and existing team membership, and writes an audit in the same transaction. An isolated native Rust/PostgreSQL test covers public API parity, RBAC/internal token rejection, unique registration, state errors, team cleanup, restricted PostgreSQL grants and forced audit rollbacks. Python fallback remains available. Production writer grants have not been provisioned, and automated scheduler persistence, team creation/join, and manual transitions were migrated subsequently.

October 29 competition challenge linking: Rust-enabled public `POST /api/v1/competitions/{id}/challenges` and `DELETE /api/v1/competitions/{id}/challenges/{challenge_id}` now delegate to internal Rust `/v1/competitions/challenges/add` and `/remove`. Rust rechecks `competition.manage`, locks the competition, enforces draft/registration-only edits, rejects unpublished challenges and duplicates, computes stable appended positions, applies point overrides only in override mode, and atomically commits the link change and its required audit event. Removal remains idempotent and audited. An isolated Rust/PostgreSQL API test covers public response parity, scoring modes, duplicate/unpublished/locked cases, auth denial, position semantics, restricted-role SQL and forced audit rollbacks on both operations. Python fallback is preserved. Production requires the updated restricted writer grants for `competition_challenges`; other team administration and automated scheduler persistence, freeze/unfreeze, and manual transitions were migrated subsequently.

October 29 competition editing: Rust-enabled public `PATCH /api/v1/competitions/{id}` delegates field changes to `POST /v1/competitions/edit`, with Rust rechecking `competition.manage`, locking the row and rejecting edits to live/finished/archived competitions. Only the public editable field allowlist is accepted; explicit nulls for optional fields, timestamp validation and the existing date-order rule are supported. The competition update and required `competition.update` audit insert commit atomically. Restricted writer grants add only `SELECT (status)` and updates on editable columns plus `updated_at`. October 29 competition creation: Rust-enabled public `POST /api/v1/competitions` now delegates draft insertion to `POST /v1/competitions/create`, rechecks `competition.create` RBAC and allowlisted input in Rust, handles duplicate slugs and atomically inserts the competition with a required audit record. Full browser OIDC login and production startup remain unverified.

October 29 Rust correct-solve transaction: In Rust-enabled mode, correct submissions now delegate to `POST /v1/submissions/correct`. Rust revalidates the candidate against current database flag hash (including ownership, running status and expiration for lab flags), rechecks `submission.create` RBAC and published challenge state, serializes concurrent solves using user/challenge row locks, and commits the correct submission, standard-mode score event, per-skill competency increases and solve audit in one transaction. Duplicate solves return zero points with an attempt audit. FastAPI retains Keycloak authentication, rate limits, badge awards and recommendation/difficulty follow-ups; standalone Python fallback is unchanged. The isolated live test passed for correct/duplicate solves, forbidden role, stale flag, concurrent duplicate submissions and rollback when the solve audit insert fails. The production writer role requires additional column-scoped privileges from `infrastructure/docker/security-core-role.sql`, which have **not** been provisioned or verified on production. Competition-specific dynamic/first-blood modes and production E2E authentication remain separate validation targets. Rust score event mode for this public submission path remains standard, matching its existing Python default.

October 29 incorrect-submission persistence slice: Rust-enabled incorrect flag attempts are now persisted by internal `POST /v1/submissions/incorrect`, with Rust-side `submission.create` authorization, PostgreSQL published-challenge visibility recheck, and atomic insertion of an incorrect submission plus `submission.attempt` audit. The existing FastAPI public endpoint remains intact and continues to verify the submitted flag before Rust is called; Rust never receives the plaintext candidate for persistence. The limited writer role adds only the necessary submission/audit insert privileges. The opt-in disposable-database integration test verified role rejection, row persistence and audit counts. **Correct solves, score events, competency profiles, bonuses and badges are still handled by the existing Python transactional path** and must be migrated together in a separate validated slice. This does not establish production role grants or end-to-end Keycloak health.
